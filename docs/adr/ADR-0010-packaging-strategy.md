# ADR-0010: GitHub Release packaging for the local alpha

**Status:** proposed
**Date:** 2026-07-26
**Deciders:** the project's human owner + cross-review

## Context

The MVP is not considered a finished product while it depends on cloning the
repository and installing Rust. The user needs to install Rationale from
GitHub, connect it to their agents, and update or remove it without losing the
canon. Installation must be able to update an already-installed binary with one
command, without forcing the cleanroom user to delete the earlier package by
hand.

## Options considered

### A — `cargo-dist`

Use the `[package.metadata.dist]` metadata and a workflow generated by
`cargo-dist` pinned to an exact version. Advantage: mature conventions for
tarballs, installers, and tags. Risk: the generated workflow must be verified on
every target before declaring support.

### B — our own workflow

Build with Cargo, produce archives and checksums, and publish with `gh`.
Advantage: full control and little magic. Risk: more maintenance of the
cross-platform matrix and of the installers.

## Decision proposal

Adopt `cargo-dist`'s contract and targets as the release interface, while
keeping deterministic versioned scripts (`scripts/package.*`) so CI can audit
and test every archive. Tarballs/ZIPs, SHA-256 checksums, shell/PowerShell
installers, and build provenance will be published.

`publish = false` stays: the alpha is distributed through GitHub Releases, not
crates.io.

## Consequences

- Target tier: macOS ARM64/x86_64, Linux x86_64/ARM64, and Windows x86_64.
- The alpha requires a clean-machine test, update, and rollback.
- The installer also distributes a `rationale-update` helper; the
  `rationale update` command runs it and keeps `.rationale/` and the project
  configuration.
- While Rationale is pre-1.0, the `stable` and `preview` channels are
  distinguished: the landing page cannot use `releases/latest` if the visible
  version is a prerelease; it must pin the explicit preview tag. (Since 1.0 the
  default channel is `stable`, and `releases/latest` resolves the stable
  release.)
- **Which tags are marked prerelease on GitHub.** Only `-alpha.`, `-rc.`, and
  `-dogfood.`. `beta` and final versions are published as full releases. The
  reason is operational, not cosmetic: GitHub marks as "latest" only a release
  that is not a prerelease, and `releases/latest` is exactly what the `stable`
  channel of `rationale-installer.sh/.ps1` resolves. Marking "any tag with a
  hyphen" left the seven alphas as prereleases and, with them, `stable` serving
  `v0.0.0-dogfood.7` — a dogfood build older than `install-agent` — to anyone
  installing through that channel. A version the project recommends using must
  be able to be "latest".
- A platform that does not pass the matrix is not declared supported in the
  release notes.
- Release binaries are a supply-chain surface and need checksums and
  attestation before publishing.
