# Fixture: vertical slice (Phase D2)

A deterministic fixture with **a single package**, on purpose: see
`docs/research/codebase-memory/08-workspaces-and-monorepos.md`. A multi-package
fixture would test a cross-package resolution capability that the provider does
not deliver reliably today.

## Contents

```text
fixtures/vertical-slice/
├── source/            # versioned fixture source (auth.resolveEntityRole)
├── setup.sh            # generates repo/ deterministically (always the same SHA)
├── repo/               # generated by setup.sh — NOT versioned (regenerable)
└── .rationale/
    ├── subjects/authorization.entity-scoped-staff-access.yaml
    └── records/constraint.no-global-admin-for-staff.yaml   (with approvals + binding)
```

`repo/` is not versioned because it is fully regenerable: `setup.sh` fixes the
author and dates (`GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE`) so the resulting
commit **always has the same SHA** on any machine.

## Usage

```bash
bash fixtures/vertical-slice/setup.sh
# Deterministic revision: cb878c9d598e54a2a9aa3993395513f7ccfff325
```

The `bound_revision` in `constraint.no-global-admin-for-staff.yaml` must match
this SHA exactly. If `source/` changes intentionally, update both in the same
commit: `EXPECTED_SHA` in `setup.sh` and `bound_revision` in the Record.

## What it tests

This fixture is the input of the Phase D vertical slice (`init → read Record →
resolve target → query CBM → check revision → return one compact constraint`).
The case reuses the canonical example from `Rationale_v0.5.md §2, §9, §27`
(per-entity authorization); it is not data from a real project.
